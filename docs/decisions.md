# ข้อตกลงการทำงานและสูตร

ปรับตามคำสั่งล่าสุดของผู้ใช้วันที่ 18 ตุลาคม 2026: สร้างเว็บให้ครบ ไม่ใช้โหมดสอน/แบบฝึกหัด และไม่หยุดรอตรวจเป็นเฟส

## การคำนวณ

- เงินเป็น bigint หน่วยสตางค์ภายใน pure functions ไม่ใช้ floating point คำนวณเงิน
- เงินไม่เกิน 2 ตำแหน่ง สูงสุด 999,999,999.99 บาทต่อช่อง น้ำหนักทศนิยมไม่เกิน 6 ตำแหน่ง มากกว่า 0 และไม่เกิน 999,999.999999 เปอร์เซ็นต์ไม่เกิน 2 ตำแหน่ง ช่วง 0–100 กรอกเกินให้แจ้งข้อผิดพลาด
- แบ่งเท่าหรือสัดส่วนด้วย Largest Remainder เศษเท่ากันให้คนที่เพิ่มเข้าบิลก่อน โหมดระบุยอดต้องตรงราคารายการ
- รวมค่าบริการและภาษีระดับบิล ปัดครึ่งขึ้นเป็นสตางค์ กระจายสู่รายการตามฐานราคา จากนั้นสู่คนตามส่วนแบ่งของรายการ จึงไม่เกิดยอดส่วนรวมคลาดเคลื่อนจากการปัดแต่ละรายการแยกกัน
- ราคาไม่รวม VAT: service จากราคา; VAT จากราคา + service เช่น 100, 10%, 7% = 117.70 บาท
- ราคารวม VAT: service จากราคาที่แสดง และบวก VAT ของ service เท่านั้น เช่น 100, 10%, 7% = 110.70 บาท VAT ที่แฝงในราคาแสดงแยกเพื่ออ้างอิง
- ส่วนลดหักหลังค่าบริการและภาษี กระจายตามยอดก่อนลดรายคน ห้ามมากกว่ายอดรวม
- หนึ่งบิลมีผู้จ่ายหน้าร้านคนเดียวจากคนในบิล เลขพร้อมเพย์ในโปรไฟล์ต้องตรงกับผู้จ่าย
- settleBalances จับคู่ยอดสุทธิแบบ greedy ตามลำดับข้อมูลที่แน่นอน ไม่อ้างว่าเป็นคำตอบจำนวนการโอนน้อยที่สุดในทุกกรณี

## การเก็บข้อมูล

Guest จำกัด 4 คน มี versioned localStorage ที่เก็บบิลยังกรอกไม่ครบได้ และสำรอง JSON ได้ ส่วนสมาชิกบันทึกบน Supabase ด้วยปุ่มบันทึก รองรับนำเข้าบิล Guest โดยยังเก็บสำเนาเดิมในเครื่อง

JSON เก็บตัวเลขทศนิยมเป็นข้อความ ฐานข้อมูลมี bigint หน่วยสตางค์เป็น relational projection พร้อม draft JSON เพื่อแก้ไข ฟังก์ชัน save_bill แก้สองส่วนใน transaction เดียวและตรวจ version ป้องกันเขียนทับบิลที่แก้จากหน้าต่างอื่น

RLS จำกัดเจ้าของทุกตาราง ลิงก์สาธารณะใช้ token สุ่ม เก็บ hash อ่านผ่าน RPC เท่านั้น และเพิกถอนได้ สถานะโอนเป็นข้อมูลที่ผู้ใช้ทำเครื่องหมายเอง

## การตรวจงาน

ทดสอบ unit/property, validation, storage, QR, PostgreSQL/RLS และ Playwright flows รวมถึง PNG/offline/หน้าจอมือถือ การตรวจ Auth และ Realtime บน Supabase hosted รวมถึงสแกน QR กับธนาคารจริงยังต้องทำหลังตั้งค่าบริการจริง ดูวิธีรันใน README.md
